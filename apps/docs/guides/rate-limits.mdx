## Overview

ByteSend enforces rate limits on API requests to ensure fair usage and platform stability. Rate limiting is applied per team per second and is measured using a sliding window.

<Note>
Rate limits only apply to the cloud-hosted version of ByteSend. Self-hosted deployments have no rate limiting.
</Note>

---

## How Rate Limiting Works

Each API request increments a counter scoped to your team. The counter resets every **1 second**. If your team exceeds the allowed number of requests within that window, subsequent requests receive a `429 RATE_LIMITED` response until the window resets.

Your rate limit is determined by your plan and is set per team at the account level.

---

## Rate Limit Headers

Every API response includes these headers so you can monitor your usage in real time:

| Header              | Description                                                        |
| ------------------- | ------------------------------------------------------------------ |
| `X-RateLimit-Limit` | Maximum requests allowed per second for your team                  |
| `X-RateLimit-Remaining` | Requests remaining in the current second window                |
| `X-RateLimit-Reset` | Unix timestamp (seconds) when the current window resets            |
| `Retry-After`       | Seconds to wait before retrying (only present on `429` responses)  |

```
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 7
X-RateLimit-Reset: 1750000042
```

## Handling 429 Responses

When you receive a `429 RATE_LIMITED` response, wait for the number of seconds specified in the `Retry-After` header before retrying:

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "Rate limit exceeded. Try again in 1 seconds."
  }
}
```

### Retrying in your code

The SDKs report a rate-limited request as a `RATE_LIMITED` error rather than retrying for you, so wrap sends that might burst in a short retry loop:

<CodeGroup>

```ts Node.js
import { ByteSend } from "bytesend-js";

const bytesend = new ByteSend();

type SendPayload = Parameters<typeof bytesend.emails.send>[0];

async function sendWithRetry(payload: SendPayload, maxRetries = 3) {
  for (let attempt = 0; ; attempt++) {
    const result = await bytesend.emails.send(payload);
    if (result.error?.code !== "RATE_LIMITED" || attempt === maxRetries) {
      return result;
    }
    await new Promise((resolve) => setTimeout(resolve, 2 ** attempt * 1000));
  }
}
```

```python Python
import time
from bytesend import ByteSend, ByteSendHTTPError

client = ByteSend()

def send_with_retry(payload: dict, max_retries: int = 3):
    for attempt in range(max_retries + 1):
        try:
            return client.emails.send(payload)
        except ByteSendHTTPError as err:
            if err.status_code != 429 or attempt == max_retries:
                raise
            time.sleep(2 ** attempt)
```

```go Go
func sendWithRetry(ctx context.Context, client *bytesend.Client, payload bytesend.SendEmailPayload) (bytesend.CreateEmailResponse, error) {
    const maxRetries = 3
    for attempt := 0; ; attempt++ {
        resp, err := client.Emails.Create(ctx, payload)
        var apiErr *bytesend.ErrorResponse
        if !errors.As(err, &apiErr) || apiErr.StatusCode != http.StatusTooManyRequests || attempt == maxRetries {
            return resp, err
        }
        time.Sleep(time.Duration(1<<attempt) * time.Second)
    }
}
```

```bash cURL
# Honour Retry-After when calling the API directly
curl -i -X POST https://bytesend.cloud/api/v1/emails \
  -H "Authorization: Bearer $BYTESEND_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"from": "hello@example.com", "to": "user@example.com", "subject": "Hi", "html": "<p>Hi</p>"}'
```

</CodeGroup>

When calling the REST API directly, wait for the number of seconds in the `Retry-After` header instead of a fixed backoff.

## Best Practices

<AccordionGroup>
  <Accordion title="Batch your requests">
    Use the [batch email endpoint](/api-reference/emails/batch-email) to send up to 100 emails in a single API call instead of making one request per recipient.
  </Accordion>
  <Accordion title="Monitor remaining quota">
    Check `X-RateLimit-Remaining` on each response. When it drops to 0, wait until `X-RateLimit-Reset` before sending the next request.
  </Accordion>
  <Accordion title="Use queues for high-volume sends">
    For large campaigns, use a background job queue (BullMQ, Redis Queue, etc.) to pace your API calls rather than sending all at once in a tight loop.
  </Accordion>
  <Accordion title="Don't retry immediately">
    Always respect the `Retry-After` header. Immediate retries on `429` responses won't succeed and waste your quota window.
  </Accordion>
</AccordionGroup>
